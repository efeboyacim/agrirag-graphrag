# Evaluation

Full per-case numbers live in [`evals/reports/latest.md`](../evals/reports/latest.md),
regenerated by `uv run python -m evals.report`. This document is about the method.

## Measured baseline

35 goldens, Claude Sonnet 5 as both the system model and the judge.

| Layer | Metric | Mean | Median | Threshold |
|---|---|---:|---:|---:|
| Retrieval | ContextualRecall | 0.92 | 1.00 | 0.80 |
| Retrieval | ContextualPrecision | 0.73 | 0.88 | 0.65 |
| Retrieval | ContextualRelevancy | 0.43 | 0.39 | 0.35 |
| Retrieval | **RoutingAccuracy** | **1.00** | 1.00 | 1.00 |
| Retrieval | **GraphPathRecall** | **1.00** | 1.00 | 1.00 |
| Generation | Faithfulness | 1.00 | 1.00 | 0.90 |
| Generation | AnswerRelevancy | 0.91 | 1.00 | 0.75 |
| Generation | Hallucination | 0.90 | 1.00 | 0.75 |
| Generation | AgronomicUsefulness | 0.93 | 0.90 | 0.75 |
| Generation | **CorrectAbstention** | **1.00** | 1.00 | 1.00 |

Bold rows are deterministic - no model, no variance, asserted per case.

### Why ContextualRelevancy is low, and why that is not a graph problem

0.43 is by far the lowest number here, and the first explanation written for it
was wrong. The assumption was that graph traversal returns many rows and drags
relevancy down. Measured by context type, the opposite holds:

| Context type | Avg chars per item | Relevancy |
|---|---:|---:|
| Graph rows (one linearised fact each) | 165-307 | **0.53** |
| Corpus chunks (multi-sentence passages) | ~580 | **0.39** |

The metric judges each *statement* inside each context item. A multi-sentence
chunk loses points for the sentences that do not bear on the question, even when
it is exactly the right chunk to have retrieved. Graph rows score better because
each one is a single fact.

So the lever for raising this number is **chunk granularity**, not retrieval
strategy - and the threshold reflects the measured baseline rather than an
invented rationale.

## The split that matters

Metrics are separated by **what they read**:

| Layer | Reads | A failure means |
|---|---|---|
| Retrieval | `retrieval_context` only | the system fetched the wrong facts |
| Generation | the answer (+ ground truth) | the system wrote a bad answer over the right facts |

Those need different fixes - ingestion and traversal versus prompting and model
choice - so collapsing them into one "quality" number would tell you something
is wrong and nothing about where.

The mechanism that makes the split real is in the agent: `AgentResult` carries
`answer` and `retrieval_context` as separate fields, and graph rows are
linearised into sentences before entering `retrieval_context`. That is what lets
DeepEval's contextual metrics score graph facts and text chunks with the same
metric, which would otherwise be impossible - one is a table, the other is prose.

## Metrics

### Retrieval

| Metric | Judged? | Diagnoses |
|---|---|---|
| `ContextualRecall` | LLM | Did retrieval find the facts the answer needs? Low means an ingestion gap or a missed hop - no amount of prompt work fixes it. |
| `ContextualPrecision` | LLM | Are relevant items ranked above noise? Low means `k` too high or a Cypher template too broad. |
| `ContextualRelevancy` | LLM | Is the material on topic, statement by statement? Driven by chunk granularity, not by routing - see above. |
| `RoutingAccuracy` | **no** | Did the router pick an acceptable path? |
| `GraphPathRecall` | **no** | Did entity linking resolve the nodes the traversal needed? |

### Generation

| Metric | Judged? | Diagnoses |
|---|---|---|
| `Faithfulness` | LLM | Is every claim supported by the retrieved context? The headline safety metric. |
| `AnswerRelevancy` | LLM | Does the answer address the question asked? |
| `Hallucination` | LLM | Does the answer align with ground truth? Higher is better in DeepEval 4.x, which reversed the direction from earlier releases. |
| `AgronomicUsefulness` | LLM (GEval) | Would this let a farmer act? |
| `CorrectAbstention` | **no** | Did it decline exactly when it should? |

## Why three metrics are deterministic

Every judged metric is slow, costs money, and moves between runs even when the
code does not. The three non-judged ones are free, instant and exactly
reproducible, which buys two things:

1. **They are cheap to gate on.** Scoring needs no judge model and costs
   nothing. The agent run being scored still needs an LLM - routing is a model
   call - so in CI they run whenever a provider key is configured. Without one,
   CI only checks that the suite collects; see the Evaluation job in ci.yml.
2. **They disambiguate judge variance from regression.** When faithfulness drops
   three points, the question is always "did something break, or did the judge
   have a different day?" If routing accuracy and entity linking are unchanged,
   it was the judge.

They also attribute failures the judged metrics cannot. A low faithfulness score
says the answer was not grounded; it does not say whether retrieval fetched the
wrong facts or the router sent the question to the wrong store. `RoutingAccuracy`
and `GraphPathRecall` answer exactly that, and during development they caught
four real bugs that the judged metrics only registered as vague low scores:

- `ClimateZone` was missing from the fulltext index, so climate questions could
  never resolve an entity - the template took a `climate_id` nothing could produce.
- Neo4j's fulltext analyzer does not stem, so "grapes" never matched the stored
  name "Grape".
- Adding singularisation then made "pests" match the stored name "Sunn pest",
  so category words had to become stopwords.
- The agent answered "what will the wheat price be next season?" from a
  tangentially-matching chunk instead of declining.

## Abstention is a first-class case

Five of the 35 goldens must be declined. They are the easiest goldens to leave
out and the most valuable to include: without them every metric rewards a system
that answers everything confidently, because there is no case where declining is
correct.

`CorrectAbstention` penalises both directions. A hallucination metric alone would
happily reward a system that refuses everything - refusing never hallucinates -
so something has to make over-caution costly too.

Abstention cases carry no contextual scores. They have no retrieval context by
design, so a contextual metric has nothing to measure and a faithfulness score
over an empty context is meaningless rather than zero.

## `context` vs `retrieval_context`

The goldens carry both, and DeepEval treats them differently:

- `retrieval_context` is **what the system fetched**. Faithfulness measures the
  answer against this.
- `context` is **what is true** - hand-written ground truth. Hallucination
  measures the answer against this.

An answer can be perfectly faithful to bad context and still be false. Only the
second comparison catches that, which is why both fields exist.

## Running it

```bash
docker compose up -d
uv run agrirag-seed --reset && uv run agrirag-index --extract

uv run python -m evals.runner --refresh   # run the agent over the goldens (~90s)
uv run python -m evals.report             # score and regenerate the report

uv run pytest evals/                      # the CI gate: thresholds enforced
```

The agent runs are cached to `evals/runs/latest.json` on purpose. Both suites
need the same outputs, so running the agent twice would double the cost and -
worse - score retrieval and generation against *different* runs, making the two
numbers incomparable. Caching also separates "run the agent" from "score the
outputs", so iterating on a metric or a threshold costs nothing.

## Judge variance, and why thresholds are aggregates

Two consecutive report runs over the *same* cached agent outputs - the only
variable being the judge - moved by up to 0.06:

| Metric | Run 1 | Run 2 | Delta |
|---|---:|---:|---:|
| Faithfulness | 0.99 | 1.00 | +0.01 |
| ContextualRelevancy | 0.44 | 0.43 | -0.01 |
| AnswerRelevancy | 0.88 | 0.91 | +0.03 |
| ContextualPrecision | 0.78 | 0.73 | -0.05 |
| AgronomicUsefulness | 0.87 | 0.93 | +0.06 |
| RoutingAccuracy / GraphPathRecall / CorrectAbstention | 1.00 | 1.00 | 0.00 |

Two consequences:

1. **Judged thresholds sit ~0.10 below baseline.** A 0.05 margin would produce
   false failures from judge noise alone.
2. **Judged metrics are asserted on the mean, not per case.** Gating every case
   on an LLM judge means a red build most days, and a red build most days is one
   nobody reads. Per-case scores still land in the report, which is where you go
   to diagnose a specific failure.

The deterministic three do not move at all. That is exactly why they are the ones
gated per case, and why they - not the judged metrics - are the CI signal that a
change actually broke something.

## Cost control

The judge is Claude via the same Portkey gateway as the application, on a
separate config so evaluation traffic stays distinguishable in the traces. That
config deliberately has **no fallback chain**: a judge that silently degraded to
a smaller model would make scores incomparable between runs.

Two knobs:

- `EVAL_SUBSET=8` scores a balanced subset, round-robin across categories so a
  reduced run does not quietly become "only graph questions". CI uses this on
  pull requests.
- Scoring concurrency is set to 2 in `evals/report.py`. Higher values trip the
  Anthropic workspace token-per-minute limit, and a rate-limited metric scores
  0.0 - which reads as a catastrophic quality collapse when nothing is wrong.

## Confident AI

Optional throughout. `deepeval` the library does all the work locally and needs
no account. Setting `CONFIDENT_API_KEY` additionally pushes results to the
Confident AI dashboard for regression tracking across runs; without it,
everything stays local and the committed Markdown report is the record.
