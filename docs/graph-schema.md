# Graph Schema

The agricultural knowledge graph: 8 domain node labels and 12 relationship types,
plus two provenance labels populated in Phase 2.

Sized deliberately. Large enough that realistic questions need two or more hops,
small enough that the whole schema still fits in an LLM prompt without crowding
out the question.

The authoritative definition is [`schema.py`](../src/agrirag/graph/schema.py) -
this document is generated from it. The loader, the migrations and the Phase 2
prompts all read the same specs, so a new label cannot drift out of sync with the
code that loads it.

## Modelling decisions worth defending

**One `Pest` label, not `Pest` + `Disease`.** A `category` property distinguishes
insect, fungal_disease, bacterial_disease, viral_disease, weed and nematode.
Separate labels would have doubled the relationship types (`TREATED_BY` twice,
`SUSCEPTIBLE_TO` twice) for no gain in expressiveness.

**`ClimateZone` is a node, not a property of `Region`.** This is what makes
"which crops suit humid subtropical zones?" a traversal
(`Crop -> Region -> ClimateZone`) rather than a property filter. Modelling it as a
string would have removed a hop that the demo depends on.

**`RECOMMENDED_FOR` is polymorphic.** A practice may be recommended for a crop or
for a soil type. The loader groups rows by target label and runs one statement per
label, because Cypher cannot parameterise a label.

**`ROTATES_WITH` is stored in one direction only.** Rotation is symmetric, so
storing both directions would double the edges and risk them diverging. Every
query must match it undirected: `(a)-[:ROTATES_WITH]-(b)`.

**Regulations vary by region.** `APPLIES_IN` is not uniform: Turkish plant
protection rules apply in all five regions, while EU instruments apply to the
export-facing ones. Without that variation, "is it restricted there?" would have
the same answer everywhere and the fourth hop would be decorative.

## Generated schema

```
NODE LABELS
  (:Crop {id, name, scientific_name, category, growing_season})
      A cultivated crop species.
  (:Region {id, name, country, avg_rainfall_mm, avg_temp_c})
      A named agricultural production region.
  (:ClimateZone {id, name})
      A climate classification that a region belongs to.
  (:SoilType {id, name, texture, ph_min, ph_max, drainage})
      A soil class with its agronomic properties.
  (:Pest {id, name, scientific_name, category})
      A pest, pathogen or weed. The 'category' property distinguishes insect, fungal_disease, bacterial_disease, viral_disease, weed and nematode.
  (:Input {id, name, input_type, active_ingredient, npk, organic_approved})
      An agricultural input: fertilizer, pesticide, fungicide, biocontrol or amendment. 'organic_approved' marks inputs permitted in certified organic production.
  (:Practice {id, name, category, description})
      A farming practice or technique.
  (:Regulation {id, name, jurisdiction, authority, effective_date})
      A regulatory or compliance instrument governing input use.

RELATIONSHIPS
  (:Crop)-[:GROWN_IN {suitability, typical_yield_t_ha}]->(:Region)
      The crop is commercially grown in the region.
  (:Region)-[:HAS_CLIMATE]->(:ClimateZone)
      The region falls in this climate zone.
  (:Region)-[:HAS_SOIL {prevalence}]->(:SoilType)
      The soil type occurs in the region.
  (:Crop)-[:SUITED_TO {ph_min, ph_max}]->(:SoilType)
      The crop performs well on this soil type within the given pH band.
  (:Crop)-[:SUSCEPTIBLE_TO {severity, growth_stage}]->(:Pest)
      The crop is attacked by this pest, at the given severity and growth stage.
  (:Pest)-[:TREATED_BY {efficacy, application_rate, phi_days}]->(:Input)
      The pest is controlled by this input. 'phi_days' is the pre-harvest interval in days that must elapse between application and harvest.
  (:Pest)-[:PREVALENT_IN {season}]->(:Region)
      The pest is an established problem in the region during this season.
  (:Practice)-[:RECOMMENDED_FOR {evidence}]->(:Crop|SoilType)
      The practice is recommended for this crop or soil type.
  (:Practice)-[:MITIGATES {mechanism}]->(:Pest)
      The practice reduces pressure from this pest by the stated mechanism.
  (:Input)-[:RESTRICTED_BY]->(:Regulation)
      Use of the input is restricted or governed by this regulation.
  (:Regulation)-[:APPLIES_IN]->(:Region)
      The regulation is in force in this region.
  (:Crop)-[:ROTATES_WITH {benefit}]->(:Crop)
      The two crops are a recommended rotation pair. Stored in one direction only - always match it undirected.```

## Indexes and constraints

Generated by `build_migrations()` and written to
[`migrations.cypher`](../src/agrirag/graph/migrations.cypher) on every seed run:

- A uniqueness constraint on `id` for every label above, plus `Document` and `Chunk`.
- A fulltext index `entity_names` over `name` and `aliases` for `Crop`, `Region`,
  `SoilType`, `Pest`, `Input` and `Practice`.

The fulltext index is what entity linking uses in Phase 3: a question mention is
resolved to a canonical node id, and that id is passed to Cypher as a parameter.
Resolving entities *before* generating a query is the single biggest reliability
win available - it removes the most common text-to-Cypher failure, which is the
model inventing a name that does not exist in the data. Aliases carry the Turkish
names (`bugday`, `misir`, `sune`), so a question in either language resolves.

## Provenance (Phase 2)

`(:Chunk)-[:PART_OF]->(:Document)` and `(:Chunk)-[:MENTIONS {confidence}]->(:Entity)`
link the vector store back to the graph. Embeddings live in LanceDB; the graph
holds only the text and the links. That is what lets a semantic hit be traced back
to the entities it discusses.

## Headline queries

These are pinned as integration tests in
[`test_graph_seed.py`](../tests/integration/test_graph_seed.py). They are the
argument for using a graph at all - flat vector search cannot answer any of them.

**Four hops.** Organic-approved treatments for maize pests in Konya, and whether
any are restricted there:

```cypher
MATCH (c:Crop {id: 'crop_maize'})-[:GROWN_IN]->(r:Region {id: 'reg_konya'})
MATCH (c)-[:SUSCEPTIBLE_TO]->(p:Pest)-[:PREVALENT_IN]->(r)
MATCH (p)-[t:TREATED_BY]->(i:Input)
WHERE i.organic_approved = true
OPTIONAL MATCH (i)-[:RESTRICTED_BY]->(reg:Regulation)-[:APPLIES_IN]->(r)
RETURN p.name, i.name, t.efficacy, t.phi_days, collect(DISTINCT reg.name) AS restrictions
```

Cotton bollworm attacks maize but is not established in Konya. The
`PREVALENT_IN` hop is what excludes it - and that hop is precisely what a
similarity search over text has no way to perform.

**Branching, not a chain.** Practices for wheat on clay soils that also reduce
rust pressure:

```cypher
MATCH (c:Crop {id: 'crop_wheat'})-[:SUITED_TO]->(s:SoilType)
WHERE s.texture CONTAINS 'clay'
MATCH (pr:Practice)-[:RECOMMENDED_FOR]->(target)
WHERE target = s OR target = c
OPTIONAL MATCH (pr)-[m:MITIGATES]->(:Pest {id: 'pest_yellow_rust'})
RETURN DISTINCT pr.name, m.mechanism
```

## Seed data

75 nodes and 190 relationships, hand-authored across 20 CSVs in
[`data/seed/`](../data/seed). Counts are asserted in the integration suite, so a
dropped row fails CI rather than quietly shrinking the graph.

Domain: Turkish agriculture across five regions - Konya (semi-arid cereals),
Cukurova (Mediterranean cotton and maize), Aegean (olive and vine), Eastern Black
Sea (hazelnut) and Southeastern Anatolia (irrigated cotton and maize) - with EU
and Turkish regulatory instruments.

The data is hand-authored rather than scraped. That is what allows the Phase 5
evaluation goldens to have real ground truth: the expected entity ids for a
question are known because the same person wrote both.
